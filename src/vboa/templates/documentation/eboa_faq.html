Why are UUIDs used as primary keys instead of auto-increment IDs?

Relational databases must identify entities using primary keys.

The most common way to do this is using auto-increment IDs, which are sequential numbers that are automatically generated by the database manager. This is a very efficient way to identify entities.

However, it has some drawbacks when the information is coming from several sources and needs to be reconciled. Therefore, it implies a huge problem: the information has to be inserted sequentially by the database manager and there is no way to know the IDs in advance.

EBOA solves this issue by using UUIDs (version 1 / RFC 4122).

The Python implementation is thread safe as shown in the following Python code snippet: 

global _last_timestamp
    import time
    nanoseconds = int(time.time() * 1e9)
    # 0x01b21dd213814000 is the number of 100-ns intervals between the
    # UUID epoch 1582-10-15 00:00:00 and the Unix epoch 1970-01-01 00:00:00.
    timestamp = int(nanoseconds/100) + 0x01b21dd213814000
    if _last_timestamp is not None and timestamp <= _last_timestamp:
        timestamp = _last_timestamp + 1
    _last_timestamp = timestamp

As _last_timestamp is global, this is visible to all the threads of the same process so that they will never see the same timestamp value.

Nevertheless, this solution is not multiprocessing safe. Thus, for making the UUIDs creation multiprocessing safe, the UUID is generated including the PID of the process as the "node" field and a random number as the "clock_seq".

With all this considered, EBOA warranties the uniqueness of the generated UUIDs.
