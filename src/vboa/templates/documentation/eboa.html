EBOA documentation

Introduction

EBOA is the backend data storage and management engine for Business Operation Analysis. It stores, validates, links, updates and queries time-tagged business operation data while keeping complete traceability to the source that produced each record.

The engine is designed for systems where incoming information changes over time, arrives from several sources, and needs to be reconciled without defining a rigid data model for every new use case. It is normally used together with VBOA, which provides the visualization and operational web interface.

Purpose and scope

EBOA targets enterprise and analytical systems that need to store time-series or time-tagged operational information with flexible relationships and high traceability.

  • Complete traceability of all data, including information created inside the infrastructure.
  • Schema-less insertion, so new kinds of data can be ingested without prior database modelling.
  • Support for modern value types, including text, boolean, double, timestamp, geometry and object values.
  • Flexible links between events, annotations and explicit references.
  • Geo-query capabilities for spatial analysis.
  • Parallel insertion using RDBMS parallelism while preserving transactional consistency.
  • Fast structured access to data so users can query it dynamically according to operational needs.
  • Continuous development and continuous integration practices.

Data model and values

EBOA uses a relational model for core entities while allowing events and annotations to carry dynamic hierarchical values. This lets processors store complex semi-structured information without changing the database schema for every new value layout.

The EBOA data model is built around six high-level entities:

  • Events: time-bounded measurements or observations associated with a gauge.
  • Annotations: descriptive properties associated with explicit references.
  • Explicit references: identifiers for business entities such as objects, systems or locations.
  • Sources: received blocks of information and the metadata needed to trace and process them.
  • Alerts: notifications related to anomalies or conditions detected in the stored entities.
  • Reports: containers for analysis results.

Supported value types are:

  • Text: string values.
  • Boolean: true or false values.
  • Double: floating-point numeric values.
  • Timestamp: date and time values.
  • Geometry: geographic or spatial data.
  • Object: nested containers for hierarchical value trees.

Values are arranged as a tree. Each node has a level position, parent level and parent position. Parent nodes must be objects and final nodes must be non-object values. This gives each value a unique position in the hierarchy while preserving relational integrity.

Data ingestion and orchestration

EBOA ingestion starts by registering the operation context, the DIM signature and the source. It then inserts the required metadata, including gauges, annotation configurations, explicit references, links and alert configuration data.

Events and annotations are bulk-inserted. Depending on the insertion strategy, records can be immediately visible or inserted as hidden candidates until the deprecation pass resolves conflicts. At the end of the process EBOA updates counters, writes the ingestion status and commits the transaction.

File-based triggering can be driven by rules in triggering.xml. Rules match files through patterns or XPath expressions and execute configured commands in isolated processes. The orchestration layer supports concurrent ingestion with source-level locking, thread-safe database sessions, configurable parallel ingestion limits and detailed ingestion status tracking.


EBOA keeps ingestion robust by wrapping operations in transactions, rolling back failed ingestions, recording status in the database, and using generation time, source priority, event keys and validity periods to resolve write conflicts.

Insertion strategies

Insertion methods can be applied at operation, event and annotation levels. They define how new data becomes visible and how previous data is removed, split, hidden or superseded.

Operation-level methods

  • insert: basic insertion; event-level insertion methods are applied.
  • insert_and_erase: applies INSERT_and_ERASE logic to all events linked to gauges in the DIM signature.
  • insert_and_erase_with_priority: applies insert-and-erase logic using source priority.
  • insert_and_erase_with_equal_or_lower_priority: applies insert-and-erase logic with equal-or-lower priority handling.

Event-level methods

  • SIMPLE_UPDATE: all events are inserted and made visible.
  • INSERT_and_ERASE: events are inserted as hidden candidates; EBOA keeps the relevant events inside the source validity period and removes or splits superseded ones.
  • INSERT_and_ERASE_with_PRIORITY: same principle as INSERT_and_ERASE, using source priority to determine relevance.
  • INSERT_and_ERASE_with_EQUAL_or_LOWER_PRIORITY: insert-and-erase using equal-or-lower priority comparison.
  • INSERT_and_ERASE_per_EVENT: uses each event period as the validity scope.
  • INSERT_and_ERASE_per_EVENT_with_PRIORITY: per-event validity with priority-based selection.
  • INSERT_and_ERASE_INTERSECTED_EVENTS_with_PRIORITY: removes lower-priority data only where higher-priority events actually intersect it.
  • EVENT_KEYS: keeps the events with the same event key and DIM signature that have the greatest generation time.
  • EVENT_KEYS_with_PRIORITY: event-key reconciliation using source priority.
  • SET_COUNTER: sets the value of a counter gauge.
  • UPDATE_COUNTER: updates the value of an existing counter gauge.

Key Behavioral Differences

  • Visibility model: SIMPLE_UPDATE makes data immediately visible, while INSERT_and_ERASE variants keep events as hidden candidates until the deprecation pass completes.
  • Validity period scope: source-level variants apply the source validity period uniformly, while per-event variants determine validity individually for each event.
  • Conflict resolution strategy: generation-time methods prioritize earlier-generated data, priority-based methods use source priority rankings, and EVENT_KEYS methods use event-key deduplication.
  • Counter operations: SET_COUNTER and UPDATE_COUNTER are specialized methods for counter-type gauges, distinguishing between initial setting and incremental updates.
  • Intersection handling: INSERT_and_ERASE_INTERSECTED_EVENTS_with_PRIORITY removes lower-priority data only where higher-priority events actually intersect it, rather than over a broader period.

Use Case: Multi-Source Timeline Completeness

A practical example is determining completeness between planned mission timelines from different sources.

Scenario: two independent sources provide scheduling data:

  • Timeline A (lower priority): expected satellite download activities.
  • Timeline B (higher priority): expected antenna reception activities.

The goal is to identify which periods have complete coverage from both timelines.

Insertion strategy:

  • Insert Timeline A using INSERT_and_ERASE_INTERSECTED_EVENTS_with_PRIORITY.
  • Insert Timeline B using INSERT_and_ERASE_per_EVENT_with_PRIORITY with higher priority.

Behavior: when Timeline B is inserted first, events are stored as-is. When Timeline A is then inserted, EBOA reviews each time period where Timeline A has events. At intersections where Timeline B also has events, Timeline A events are removed; at gaps where Timeline B has no events, Timeline A events are kept. The result is a union of both timelines that reflects completeness.

Key difference from INSERT_and_ERASE_per_EVENT_with_PRIORITY: the per-event priority method removes Timeline A events whenever Timeline B has higher priority, even when Timeline B does not actually have conflicting events during those periods. INSERT_and_ERASE_INTERSECTED_EVENTS_with_PRIORITY only removes lower-priority data where the higher-priority source truly overlaps it.

Annotation-level methods

  • SIMPLE_UPDATE: all annotations are inserted.
  • INSERT_and_ERASE: keeps the annotation with the most relevant generation time for the annotation configuration and explicit reference.
  • INSERT_and_ERASE_with_PRIORITY: resolves annotation conflicts using source priority.

EBOA interface

EBOA offers interfaces for three general operations with data: insert, update and query. Input data can be provided as XML, JSON or a Python dictionary, and is verified against the corresponding schema before processing.

Python insert interface

The entry point for inserting data using the Python interface is the following method:

def treat_data(self, data=None, source=None, validate=True):
    """
    Method to treat the data stored in self.data
    :param data: structure of data to treat
    :param source: name of the source of the data
    :param validate: flag to indicate if the schema check has to be performed
    """

Example:

from eboa.engine.engine import Engine

engine = Engine()

data = {"operations": [{
    "mode": "insert",
    "dim_signature": {"name": "dim_signature", "exec": "exec", "version": "1.0"},
    "source": {
        "name": "source.xml",
        "generation_time": "2018-07-05T02:07:03",
        "validity_start": "2018-06-05T02:07:03",
        "validity_stop": "2018-06-05T08:07:36"
    },
    "events": [{
        "explicit_reference": "EXPLICIT_REFERENCE_EVENT",
        "gauge": {"name": "GAUGE_NAME", "system": "GAUGE_SYSTEM", "insertion_type": "SIMPLE_UPDATE"},
        "start": "2018-06-05T02:07:03",
        "stop": "2018-06-05T08:07:36"
    }],
    "annotations": [{
        "explicit_reference": "EXPLICIT_REFERENCE_ANNOTATION",
        "annotation_cnf": {"name": "NAME", "system": "SYSTEM"}
    }]
}]}

returned_value = engine.treat_data(data)

This example inserts or updates the DIM signature, source, event, gauge, explicit reference, annotation and annotation configuration records needed by the operation.

Full Stack Application: EBOA + VBOA

While EBOA serves as a powerful backend data management engine, it is designed to work seamlessly with VBOA (Visualization for Business Operation Analysis), a modern frontend component that completes the full-stack application architecture.

The EBOA + VBOA stack provides an enterprise-grade solution for business operation analysis:

  • EBOA (Backend): data storage, management and query engine built on PostgreSQL with Python API.
  • VBOA (Frontend): interactive web application for visualization, analysis and real-time monitoring.

Together, these components form a complete, production-ready platform for complex business operation management without requiring extensive custom development.

One of the key advantages of the EBOA + VBOA stack is its easily customizable architecture:

  • Modular design: both components are designed with modularity in mind, allowing you to extend and customize functionality.
  • Configuration-driven: most features are driven by configuration files rather than code changes.
  • Data model adaptation: define your own entities and relationships through EBOA's flexible schema.
  • UI customization: VBOA's interface can be tailored to your specific business needs.
  • Integration points: well-defined APIs and integration points for connecting custom processors and analyzers.

Prometheus integration

EBOA can expose operational metrics for Prometheus. This supports real-time monitoring, performance tracking, system health checks, historical analysis, Grafana dashboards and alert rules based on BOA component metrics.
