BOA tailoring

Introduction

BOA can be tailored by installing a project package on top of the generic EBOA and VBOA packages. The project package normally contains ingestion modules, additional views and BOA configuration files.

The following public repositories are examples of tailored BOA implementations:

  • s1boa: Sentinel-1 tailored BOA with ingestion modules and views for monitoring and analyzing the Earth observation mission.
  • s2boa: Sentinel-2 tailored BOA with ingestion modules and views for monitoring and analyzing the Earth observation mission.
  • bankboa: Bank-specific tailored BOA with ingestion modules and views for analyzing financial data.

They show how mission-specific and business-specific packages can reuse the same BOA data model while adding their own data model, configuration, dashboards and navigation entries.

Project layout

A tailored project normally keeps the ingestion package and the visualization package in the same source distribution. The ingestion package owns parsers and business rules. The views package owns Flask blueprints, templates, static files and the application wrapper.

The setup file exposes both packages with find_packages() and declares the generic dependencies, at least eboa and vboa, plus project-specific libraries such as pandas, xlrd, astropy or mission helpers.

Relevant configurations

Files inside boa_config are all optional. This folder is used to customize the behavior of the tailored BOA.

- File engine.json

This file allows you to define various settings for the BOA engine. The following is a list of highlights of some relevant configurations:

  • Log level: "LOG/LEVEL" setting is used to specify the log level of the BOA application. 
    {
  "LOG": {
        "LEVEL": "INFO",
        "MAX_BYTES": 50000000,
        "MAX_BACKUP": 30
    }
}
  • Number of ingestion retries: "INGESTION_RETRIES" setting is used to specify a maximum number of ingestion retries in case of failure. 
    {
  "INGESTION_RETRIES": 2
}
  • Replicate event values module: "REPLICATE_EVENT_VALUES_MODULE" setting is used to specify a custom module for handling event value replication logic when the associated event gets updated by an insertion strategy. 
    {
  "REPLICATE_EVENT_VALUES_MODULE": "myboa.ingestions.replicate_event_values"
}

    The referenced module should be packaged with the project, as done in the s2boa examples, so the EBOA engine can import it at runtime and apply the project-specific value replication policy.

- File triggering.xml

This file allows to define triggering rules for file-based ingestion. Each rule matches a file name, assigns a source type and invokes the ingestion module with eboa_ingestion.py -p package.module -f. 

<triggering_rules>
<rule>
<source_mask>MY_SOURCE_........T......_.*.xml</source_mask>
<source_type>MY_SOURCE</source_type>
<tool>
  <command>eboa_ingestion.py -p myboa.ingestions.ingestion_my_source.ingestion_my_source -f </command>
</tool>
</rule>
</triggering_rules>

When an ingestion needs previously ingested context, add dependencies to the rule. 

<dependencies>
<source_type>MY_PLANNING_SOURCE</source_type>
<source_type>MY_ORBIT_SOURCE</source_type>
</dependencies>

- File scheduler.xml

This file allows to define BOA scheduler rules. Each rule defines when it has to be triggered, the reporting window it covers and the tasks to execute. The tasks normally call rboa_triggering.py to generate reports registered in reporting_generators.xml. 

<rules>
<rule name="DAILY">
  <periodicity>1</periodicity>
  <window_delay>0.083333333</window_delay>
  <window_size>1</window_size>
  <date>
    <time>08:00:00</time>
  </date>
  <tasks>
    <task name="BOA_HEALTH">
      <command>rboa_triggering.py -g "BOA health generator" -m AUTOMATIC</command>
    </task>
  </tasks>
</rule>
</rules>

The values periodicity, window_delay and window_size are expressed in days. A rule can also include a weekday inside date for weekly schedules, as shown in the s2boa example.

- File reporting_generators.xml

This file allows to register RBOA reporting generators. VBOA uses this configuration to list executable reports in the reporting navigation, and the scheduler can trigger the same generators by name through rboa_triggering.py. 

<reporting_generators>
<generator name="My report generator" description="Generator for a tailored BOA report">
  <command>rboa_reporting.py -p myvboa.views.my_view_generator</command>
  <name_format>MY__REP__MY_VIEW_%C_%B_%E.html</name_format>
  <parameters>
    <parameter name="type">COMPLETE</parameter>
  </parameters>
</generator>
</reporting_generators>

The command points to the Python generator module. The name_format defines the generated report file name. Optional parameters are passed to the generator so the same module can expose different report variants, for example complete views and alerts-only views.

- File users.json

This file allows to import UBOA users and roles into the BOA instance. It follows the same operation-based structure used by the users management import and export actions. 

{
  "operations": [{
    "mode": "insert",
    "roles": [{
      "name": "example_role",
      "description": "Role used by the tailored BOA"
    }],
    "users": [{
      "email": "example@example.com",
      "username": "example",
      "password": "example_hash_password",
      "roles": ["example_role"]
    }]
  }]
}

Roles must be defined before they are assigned to users. Password values must be prepared in the format expected by the UBOA import process, as in the files exported from the users management page.

Creating ingestions

An ingestion module is a Python module called by eboa_ingestion.py. Its main entry point is process_file(file_path, engine, query, reception_time). The function parses the received file and returns a dictionary with one or more BOA operations. 

def process_file(file_path, engine, query, reception_time):
    source = {
        "name": file_name,
        "reception_time": reception_time,
        "generation_time": generation_time,
        "reported_validity_start": reported_validity_start,
        "reported_validity_stop": reported_validity_stop,
        "validity_start": validity_start,
        "validity_stop": validity_stop,
        "priority": 30
    }

    event = {
        "gauge": {
            "insertion_type": "INSERT_and_ERASE",
            "name": "MY_EVENT",
            "system": "MY_SYSTEM"
        },
        "start": validity_start,
        "stop": validity_stop,
        "values": [
            {"name": "status", "type": "text", "value": "OK"},
            {"name": "amount", "type": "double", "value": 12.5}
        ]
    }

    return {
        "operations": [{
            "mode": "insert_and_erase",
            "dim_signature": {
                "name": "MY_SOURCE",
                "exec": os.path.basename(__file__),
                "version": version
            },
            "source": source,
            "events": [event]
        }]
    }

The operation defines how EBOA inserts data, the DIM signature used to identify the ingested data family, the traceable source metadata and the events, annotations or explicit references produced by the parser.

For more information on data flow, see the EBOA data ingestion and orchestration documentation.

For more information on insertion methods, see the EBOA insertion strategies documentation.

Creating views

A project view is a Flask blueprint registered by the project-specific BOA application. The blueprint queries EBOA, exports entities to a JSON-friendly dictionary and renders a template. The template is the second half of the view: it receives the dictionaries and entities prepared by the blueprint and defines the dashboard including a query form, tables, timelines, maps, summaries and all relevant information shown to the user. 

from flask import Blueprint, current_app, render_template, request
from vboa.security import auth_required, roles_accepted
from vboa import functions as vboa_functions
from eboa.engine.query import Query
from eboa.engine import export as eboa_export

bp = Blueprint("my_view", __name__, url_prefix="/views")
query = Query()
version = "1.0"

@bp.route("/my-view", methods=["GET", "POST"])
@auth_required()
@roles_accepted("administrator", "service_administrator", "operator", "analyst", "operator_observer", "observer")
def show_my_view():
    current_app.logger.debug("My tailored view")
    filters = request.form.to_dict(flat=False).copy() if request.method == "POST" else {}
    start_filter, stop_filter = vboa_functions.get_start_stop_filters(filters, 30, 30)

    data = {"metadata": {
        "version": version,
        "reporting_start": stop_filter["date"],
        "reporting_stop": start_filter["date"]
    }}

    events = query.get_events(
        gauge_names={"filter": "MY_EVENT", "op": "=="},
        stop_filters=[{"date": data["metadata"]["reporting_start"], "op": ">"}],
        start_filters=[{"date": data["metadata"]["reporting_stop"], "op": "<"}],
        order_by={"field": "start", "descending": False})

    eboa_export.export_events(data, events, group="my_events", include_ers=False, include_annotations=True, include_alerts=True)
    return render_template("views/my_view/my_view.html", data=data)

Templates are usually located under the project VBOA package, usually in templates/views/<view_name>/. The main template normally extends panel/index.html, fills the content block and, when JavaScript is needed, fills the scripts block. Larger views can be split into reusable partial templates with {% raw %}{% include %}{% endraw %}.

Common template patterns in tailored views are:

  • Main page: defines the title, query or sliding-window forms, and the top-level layout.
  • Content parts: keep large tables, warning panels, summaries or map sections in smaller files.
  • Common parts: reuse shared controls, for example mission selectors, start/stop filters, orbit filters, headers and pagination.
  • Script parts: load page-specific JavaScript for charts, timelines, maps or AJAX refreshes through the scripts block.

Application wrapper and navigation

The project VBOA package wraps the generic VBOA application. It registers project blueprints and prepends its templates folder with jinja2.ChoiceLoader. This lets the project override panel/index.html while keeping all generic VBOA templates available. 

import os
import jinja2
import vboa
from myvboa.views.my_view import my_view

def create_app():
    app = vboa.create_app()
    app.register_blueprint(my_view.bp)

    templates_folder = os.path.dirname(__file__) + "/templates"
    app.jinja_loader = jinja2.ChoiceLoader([
        jinja2.FileSystemLoader(templates_folder),
        app.jinja_loader
    ])

    return app

Add menu entries by overriding the side_panel_plugins block in the project templates/panel/index.html.

Finally, expose the tailored application with a WSGI entry point: 

from myvboa import create_app

app = create_app()

Implementation checklist

  1. Create the project packages, for example myboa and myvboa.
  2. Add ingestion modules under myboa/ingestions/ and implement process_file.
  3. Return BOA operations containing source metadata, DIM signatures and generated entities.
  4. Add boa_config/triggering.xml rules for every source family and dependency chain.
  5. Create Flask blueprints under myvboa/views/ for project dashboards or analysis pages.
  6. Register the blueprints in myvboa.create_app() and prepend the project templates folder.
  7. Override templates/panel/index.html to add navigation through side_panel_plugins.
  8. Declare dependencies and package data in setup.py and MANIFEST.in.
  9. Install the package in the BOA environment and ingest representative files through the triggering rules or manual ingestion page.
  10. Verify the generated events in EBOA navigation, then validate the tailored views with realistic reporting windows.
